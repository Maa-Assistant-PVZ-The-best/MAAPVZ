# SPEC —— SelectPlants 动态回顶（本轮下滑次数 + 3）

> 事实来源：`agent/select_plant/custom_select_plant.py`
> 本文件记录**为什么这么改**与**验收标准**，实现以 `.py` 为准。

## 1. 问题

旧默认值（写死）：

```python
DEFAULT_BACKTOP = {"begin": [381, 401], "end": [381, 611], "repeat": 30, "duration": 80}
```

- `repeat: 30` 写死在 Python 内：每次回顶**无条件上滑 30 次**（30×80ms ≈ 2.4s + IPC），
  列表只有几屏时纯属浪费，列表很长时又可能不够。
- 次数与「本次实际往下滑了几次」完全脱钩，所以既不灵活也不需要存在这个默认值。

## 2. 目标（用户口径）

1. `DEFAULT_BACKTOP` 精简为：

```python
DEFAULT_BACKTOP = {"begin": [381, 401], "end": [381, 611], "duration": 600}
```

2. 回顶**次数 = 本轮实际下滑次数 + 3**（动态，不写死）。
3. ❗ **不能**把回顶改成「滑动坐标反向上滑」——实测会有 bug。
   回顶就用自己那组坐标（381,401 → 381,611，往下刷 = 列表往上翻）。

## 3. 前置解耦：扫描步数 ≠ 重试轮数

旧代码里「往下滑一步」和「retry」是同一个计数器（`retry <= max_retry`，默认 6），
所以一个植物最多只往下扫 6 屏，**根本滑不到列表深处**；旧实现是靠 `repeat=30` 硬顶着。

改成：

| 参数 | 默认 | 含义 |
|---|---|---|
| `最多滑动步数` | 40 | 单轮**向下扫描**上限（滑到底由保底机制判定，不靠这个数） |
| `最多重试` | 6 | **回顶重扫**上限（语义与旧版一致） |

- 下滑一步 → `slide_count += 1`，到 `最多滑动步数` 就回顶重扫；
- 触发保底（连续 `保底连续帧` 次滑动画面无变化）→ 判定到达列表尽头 → `retry += 1` + 回顶；
- 每轮回顶后 `slide_count` 清零 —— 于是「+3」永远贴合列表真实长度。

## 4. 兼容

- 参数里**显式**给了 `回顶.repeat` / `回顶.begin` / `回顶.end` → 仍走旧行为（固定次数）。
  没给 → 动态次数；`begin/end/duration` 从 `DEFAULT_BACKTOP` 取，可被 `回顶` 部分覆盖。
- `回顶.duration` 缺省 600（旧的 80 是配 30 连刷用的；次数动态后 600 更稳）。
- pipeline JSON 无需改动（`02_..._Choose_ref.json` 传 `{}`，`debug.json` 只传植物列表）。

## 5. 验收标准

1. 本轮下滑 2 次 → 回顶 5 次；下滑 5 次 → 回顶 8 次（严格 `N+3`）。
2. 回顶用地是 `(381,401) → (381,611)`，**不是**滑动的反向坐标。
3. 保底触发时回顶次数 == 本轮下滑数 + 3，且 `retry` 每次保底只 +1。
4. `最多滑动步数` 生效，不会无限下滑。
5. 旧写法（显式 `repeat`）行为不变。
6. 一个植物**已经滑到列表尽头**时不会死循环。
